Preparing a public release

DendriNet uses the existing institutional repository and its accepted core history. Private extensions and local archive branches are not part of a public release. A release does not require rewriting that history or changing the versions used by scientific studies.

Package boundary

The installed package contains dendritic_modeling and its small tutorial configurations. projects/ holds study-specific code and apps/ holds optional applications; neither is included in the core distribution. The source distribution also contains the reference configs, tests and docs. setup/check_distribution.py checks the built archives against this boundary.

Release order

Build and review both packages in one pull request to develop. After merging, tag the reviewed source, stage the wheels and source archives on TestPyPI, and promote the tested files to PyPI. Publish core first so a normal installation of Studio can resolve its dependency. Pull requests and pushes to develop build and test the packages without uploading to an index. TestPyPI uploads are publicly downloadable too.

The examples below use core 0.5.0 and Studio 0.1.0. Substitute the approved versions for another release.

1. Prepare the release pull request

  • Set the core version in pyproject.toml and src/dendritic_modeling/__init__.py. Set the Studio version in apps/studio/pyproject.toml and apps/studio/src/dendrinet_studio/__init__.py. For this stable pair, use dendritic_modeling>=0.5.0,<0.6 in Studio’s dependencies. Include the release notes in CHANGELOG.md.

  • Push only the reviewed candidate branch and open its PR against develop. Review the package contents and any public study examples. The Package release check builds both source archives and wheels, checks metadata with Twine and inspects the core archive. It also installs both wheels outside the checkout, runs the installed examples and sweep checks, and exercises the Studio browser tests. Check the documentation build and the ordinary core test suite alongside the packaging job.

  • Merge after review and passing CI. Record the merge commit from the PR and verify the checks on develop. The documentation workflow also deploys the Sphinx site to the Pages branch on this push. The hosted page is the Studio manual. The application runs locally. Under Settings → Pages, verify the publishing source and access for the intended readers. Before announcing public documentation, open the Studio guide in a signed-out browser and check that the new walkthrough and figures load.

2. Set up publishing access

This one-time setup can be done while the PR is under review.

  1. Use maintainer accounts on both PyPI and TestPyPI. The indices use separate accounts.

  2. In the institutional GitHub repository, create the Actions environments testpypi and pypi. If you restrict deployments by ref, allow the release tags for both packages (v* and studio-v*). Configure a production reviewer if your repository plan supports it.

  3. For each package on each index, configure a GitHub Trusted Publisher. Use owner KempnerInstitute, repository DendriNet and workflow filename package.yml. On TestPyPI use environment testpypi; on PyPI use pypi. The two project names are dendritic-modeling (Python import dendritic_modeling) and dendrinet-studio. For a new project, create a pending publisher in the account’s Publishing settings. For an existing project, its owner adds the publisher in project settings. A pending publisher does not reserve a name. See the PyPI instructions.

The workflow requests a short-lived publishing credential for its GitHub environment. No upload token is needed in repository secrets. Repository visibility is a separate maintainer decision. Review the remote branches, tags and artifacts that will be visible before changing it.

3. Tag the reviewed merge

From an authenticated clone, set release_commit to the merged PR’s full commit SHA. Verify its ancestry and versions before creating tags. If the branch has advanced, keep the reviewed SHA.

git fetch origin develop
git merge-base --is-ancestor "$release_commit" origin/develop
git show "${release_commit}:pyproject.toml"
git show "${release_commit}:apps/studio/pyproject.toml"
git tag -a v0.5.0 "$release_commit" -m "DendriNet 0.5.0"
git tag -a studio-v0.1.0 "$release_commit" -m "DendriNet Studio 0.1.0"
git push origin refs/tags/v0.5.0 refs/tags/studio-v0.1.0

Use a remote configured for authorized pushes. The release check requires the tag to match the distribution’s declared version and its commit to be in the history of origin/develop. Pushing a tag alone does not upload files.

4. Stage and install both packages from TestPyPI

Use an authenticated GitHub CLI on your workstation. GitHub registers a manually dispatched workflow from the repository’s default branch, which must already contain .github/workflows/package.yml. Pass the tag as the workflow ref. See the GitHub manual dispatch guide.

repo=KempnerInstitute/DendriNet
gh workflow run package.yml --repo "$repo" --ref v0.5.0 \
  -f distribution=core -f target=testpypi
gh workflow run package.yml --repo "$repo" --ref studio-v0.1.0 \
  -f distribution=studio -f target=testpypi

In GitHub Actions, record the numeric run ID from each run’s URL (/actions/runs/<ID>) with its distribution and tag. Wait for both runs, including their upload jobs, to succeed. Run the following outside the source checkout in an empty directory and a fresh environment. Download only the two candidate wheels from TestPyPI. Pip will resolve their normal dependencies from the production index at installation.

python -m venv .venv
. .venv/bin/activate
python -m pip download --index-url https://test.pypi.org/simple/ \
  --only-binary=:all: --no-deps --dest wheels \
  'dendritic-modeling==0.5.0' 'dendrinet-studio==0.1.0'
python -m pip install --index-url https://pypi.org/simple/ wheels/*.whl
python -m pip check
dendritic-example synthetic_population --output demo.yaml
dendritic-train demo.yaml --epochs 1
dendrinet-studio --workspace studio-check

Open the printed URL, run Check model, and train the synthetic example on CPU as described in Train your first network. Keep the results of this clean-install check and the two staging run IDs. The packaging guide to TestPyPI explains why dependencies are downloaded separately.

5. Promote core, then Studio

Set core_stage_id and studio_stage_id to the respective IDs from step 4. Run the first command and wait for a successful publish job. Then run the second and wait for it to succeed.

gh workflow run package.yml --repo "$repo" --ref v0.5.0 \
  -f distribution=core -f target=pypi -f staging_run_id="$core_stage_id"
gh workflow run package.yml --repo "$repo" --ref studio-v0.1.0 \
  -f distribution=studio -f target=pypi -f staging_run_id="$studio_stage_id"

For each distribution, CI verifies the staging run’s workflow, commit and success, retrieves its artifacts, then matches the wheel and source archive names, versions and SHA-256 digests to the release on TestPyPI. Production receives those exact files. If verification fails, inspect the run ID, tag and file digests before approving an upload.

Finally, in a second empty environment, install only python -m pip install dendrinet-studio==0.1.0. Run python -m pip check, inspect both installed versions with python -m pip show dendritic-modeling dendrinet-studio, and repeat the local tutorial. The core-only install is python -m pip install dendritic-modeling==0.5.0. Link the two PyPI pages and the Studio guide in the release notes. Keep research workflows on their recorded versions until their numerical comparisons qualify a newer release.

Installed examples

dendritic-example
dendritic-example synthetic_population --output demo.yaml
dendritic-train demo.yaml --epochs 1

The exporter refuses to overwrite an existing file. Tutorial settings are illustrations, not recommended hyperparameters or qualified paper recipes.

Research projects

Study protocols, sweep choices, cohort summaries and figure layouts belong in the study project. General models, training rules and analysis primitives remain in the library. A study release records its source, dependencies, resolved configurations, artifact identities and reproduction commands. See Project provenance; publication does not migrate existing pins.
